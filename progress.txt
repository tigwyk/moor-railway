## Codebase Patterns
- MCP host crate is at `crates/mcp-host/src/`; main source files: `moor_client.rs`, `mcp_server.rs`, `connection.rs`, `main.rs`
- `MoorClient` wraps ZMQ RPC calls to the mooR daemon; login uses `mk_login_command_msg` with connect_args vec where args[0] is the verb ("connect" or "create")
- `Obj` implements `Copy`, so don't use `.clone()` on it (clippy catches this)
- Login result from daemon includes: `success`, `auth_token`, `connect_type` (ConnectType enum), `player` (Obj), `player_flags` (u16) — defined in `moor_rpc.fbs`
- Reconnection always uses `LoginMode::Connect` regardless of original mode, since the player already exists after creation
- Clippy enforces collapsible `if let` chains — use `&&` syntax for nested `if let` guards
- `SessionManager` in `session_manager.rs` manages dynamic player sessions; `ConnectionManager` in `connection.rs` is the old static approach (will be replaced in US-004)
- `CreationPolicy` enum (Open/Token/AdminOnly/Disabled) lives in `session_manager.rs`; it implements `FromStr` for clap parsing and `Serialize`/`Deserialize` for figment YAML config
- `humantime` crate is available in mcp-host for parsing duration strings like "30m", "1h", "300s"
- CLI args use `String` types for enums/durations, parsed manually after figment extraction, to keep figment YAML compatibility simple
- `SessionManager` provides `_mut()` variants (`programmer_service_mut`, `wizard_service_mut`, `get_session_client_mut`) that use `Mutex::get_mut()` to bypass locking when `&mut self` is available — preferred for single-threaded `McpServer` usage
- `McpServer::get_client_for_tool(wizard, session_id)` resolves dispatch: wizard->wizard_service, session_id->session client, current_session->session client, fallback->programmer_service
- Tool arguments can include `session_id` (optional UUID string) which is extracted in `handle_tools_call` and passed through dispatch
- Session lifecycle tools (moo_session_create/login/use/close, moo_sessions_list) are meta-tools dispatched directly in `handle_tools_call`, not through the normal client dispatch path
- `moo_session_create` enforces `check_creation_policy` before creating; `moo_session_login` uses `LoginMode::Connect` (no policy check needed)
- `set_current` defaults to true on create/login; `moo_session_close` clears `current_session_id` if closing the current session
- `PlayerSession` has a background event subscription task (ZMQ subscriber) and implements `Drop` to clean it up; use `drain_events()` to retrieve buffered events
- ZMQ event subscription uses `events_recv(client_id, &mut subscriber)` and topic filter is `client_id.as_bytes()`; match on `ClientEventUnionRef` variants for event types
- `MoorClient` exposes `client_id()`, `zmq_context()`, `config()` getters for creating external subscribers
- `PlayerSession::event_buffer_arc()` returns a cloneable `Arc<Mutex<VecDeque<BufferedEvent>>>` for async event polling outside of SessionManager borrow scope

## 2026-02-07 - US-008
- Added `moo_session_events` meta-tool for polling narrative events from a player session
- Tool accepts optional `session_id` (defaults to current session) and `timeout_ms` (default: 5000)
- `timeout_ms: 0` returns immediately with whatever is buffered; `timeout_ms > 0` polls at 50ms intervals until events arrive or timeout
- Events are drained from the session's buffer and returned as `[timestamp] type: content` lines
- Added `event_buffer_arc()` method to `PlayerSession` for async polling (clones the `Arc<Mutex<VecDeque<BufferedEvent>>>`)
- Tool registered in `handle_tools_list()` and dispatched as a meta-tool in `handle_tools_call()`
- Returns "No events" when buffer is empty after timeout, or clear error when session_id is invalid/missing
- Files changed: `crates/mcp-host/src/mcp_server.rs`, `crates/mcp-host/src/session_manager.rs`
- **Learnings for future iterations:**
  - For async polling of synchronous `Mutex<VecDeque>` buffers, clone the `Arc` to release the borrow on SessionManager, then poll with `tokio::time::sleep` intervals
  - Meta-tools that need SessionManager access (not just a MoorClient) are dispatched early in `handle_tools_call` before the wizard/session_id extraction for normal tools
  - `NarrativeEventType` needs to be imported into mcp_server.rs for formatting event output
